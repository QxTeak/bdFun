# 首页推荐算法优化方案

任务：REC-00（设计）；日期：2026-11-13；状态：同一 PR 实现本地优化 v1；阶段范围和未验收项见 [实现记录](HOME_RECOMMENDATION_IMPLEMENTATION.md)。

## 1. 目标与范围

目标是接近官方推荐的相关性与连续浏览体验，并形成 bdFun 的差异化：保留服务端个性化候选，在端上减少重复、适应当前会话、控制内容疲劳。不能取得官方完整召回库、模型和内部评分，不承诺复刻官方算法，也不以停留时长最大化作为唯一目标。

按 2026-11-14 用户要求，PR #52 从方案扩展为实现，REC 阶段保留为工作与验收划分，不再要求各开独立 PR；逐阶段验收、提交和回滚。此功能是新增业务，不借迁移修改既有行为。

## 2. 当前基线与待确认事项

以 origin/main 的 9d72387 为设计基线：

- feature/home/application/HomeFeedStateHolder 负责首屏、刷新、分页及会话内排除；刷新把新视频前插，按 BV 去重。
- infra/bili/FeedApi.kt 支持 Web/App 推荐主源及另一来源兜底；默认参数为 Web，但运行时还受既有 recommendWeb 设置影响，不能直接断言所有用户都在使用 Web。
- 分页在原始返回空、或无排除条件且本批全部重复时可能结束；分类排除可能补拉详情。
- 首页曝光、满意观看、本地兴趣画像和有边界重排尚无本方案要求的完整闭环。
- core/domain 的 GeneralSettings 已有 recommendWeb；新优化开关与推荐源选择是两个独立维度，不替代、不暗改后者。

REC-01 必须检查真实响应：账号凭据是否参与请求、刷新/翻页参数语义、服务端游标、候选类型、顺序、反馈标识、原因及分类字段、原始空与过滤后空的差别。代码里的参数名和历史注释不能代替协议证据。比较同账号的 Web/App 样本后再决定是否提出单独的主源变更，不在优化开关中偷偷切源。

公开依据：[B 站个性化推荐算法说明](https://www.bilibili.com/blackboard/activity-gPIvOmhxbh.html)，描述候选召回、融合排序及播放/互动/负反馈信号；2026-11-13 查阅。本文具体公式、阈值和阶段划分均为 bdFun 设计，不是官方实现披露。真实响应样本须脱敏，不能提交 cookie、access_key、账号标识或可重放凭据。

## 3. 开关契约

设置名称：**推荐算法优化**。建议放在设置页现有首页/推荐相关区块，具体组件沿用当前设计系统。

说明文案：结合本机浏览反馈调整推荐顺序，减少重复内容。关闭后使用现有推荐方式。

- 默认关闭，升级缺失字段也为 false；单一默认值来源，不静默自动启用。
- 偏好按安装持久化；学习、曝光与观看数据按账号隔离。游客可显式开启，但只保留内存会话，进程结束即清理，不把游客数据转入登录账号。
- 关闭：旁路整个新增优化链，使用既有来源/去重/刷新/屏蔽逻辑；停止新增算法事件采集、画像更新和优化预取。既有历史、播放进度、用户主动互动和不感兴趣继续工作。
- 关闭立即使当前优化 generation 失效，取消对应子任务，拒绝迟到写入；已展示内容不跳动。下一次刷新以基线路径重建列表；已经展示的旧顺序不宣称能瞬间恢复原序。
- 开启：下一批未展示候选开始优化，当前可见内容与滚动位置保持；后台不得重排已发布列表。下拉刷新按新模式生成批次。
- 关闭不自动清画像；提供“清除推荐学习记录”，清除画像、优化曝光/观看记忆及会话缓存。关闭时也可清除。重新开启只使用未过期数据。
- 清除操作递增代数，拒绝清除前事件和任务的迟到回写；保留开关偏好，不清官方历史、收藏、关注、播放进度或既有屏蔽设置。
- 账号切换：先关闭旧账号会话再取消任务，新账号独立加载；事件携带账号作用域及模式代数，不跨账号迁移。
- 算法异常或预算耗尽：返回本批服务端顺序并保留既有明确排除；记录 debug 原因，不清空首页、不无限重试，不自动修改用户开关。

## 4. 数据与事件契约

候选需保存 video、source、batchId、sourceRank、fetchedAt、协议中已确认的上下文；不把 rank 当官方概率。字段缺失保留 Unknown，不猜分类、不用播放量代替质量。原始响应字段与领域模型通过 DTO/mapper 分隔。

算法事件包含 eventId、匿名本地账号作用域、sessionId、exposureId、bvid、来源批次、事件类型、事件时间、policyVersion 和 generation。重放应幂等；时间衰减使用可注入 Clock，停留/观看累计使用单调时钟，防止系统改时导致负时长。

| 事件 | 定义与用途 |
|---|---|
| 有效曝光 | 首页处于可交互前台、无覆盖弹层、卡片可见面积至少 50% 且连续 800ms；阈值为实验初值，预取/组合不算曝光 |
| 点击 | 关联原曝光，弱正向；搜索、动态、自动连播与首页入口分开标注 |
| 有效观看 | 实际播放区间去重累计；暂停、缓冲、seek 跳过不累计，循环不无限放大，倍速同时保留墙钟与内容区间 |
| 快速返回 | 满足实际播放前提且观看很短的弱负向；错误、缓冲失败、误触撤回不能当兴趣负反馈 |
| 明确正向 | 点赞、投币、收藏、关注分别记录，只在操作确认成功时生效；取消动作可修正原证据 |
| 明确负向 | 不感兴趣、屏蔽按用户所选作用范围处理；撤销必须幂等撤回对应证据 |

有效曝光去重单位为会话内 BV，记录次数设上限；页面旋转/重组不重复计数。观看按播放会话累计，并在退出、后台转移、画中画和恢复时衔接同一归属；后台、画中画保留场景标签并限制兴趣贡献，不能只盯 Activity 是否前台。具体满意观看函数在 REC-04 用长短视频样本标定，不能先把完播率等同满意度。

第一版数据仅在本机处理，不引入上传分析服务。事件暂定保存 7 天/每账号 10000 条，曝光记忆 7 天/5000 个 BV，聚合画像闲置 30 天过期/每账号 2000 个兴趣键，任一容量或期限达到即淘汰；所有账号合计磁盘预算暂定 20MiB，淘汰最久未活跃账号数据。写入串行、有界、批量落盘，不在主线程 IO。预算为初值，REC-02 必须验证实际大小及全局上限。

## 5. 排序与编排

流水线：官方候选 → 既有明确排除 → 优化曝光/观看去重 → 有界兴趣重排 → 多样性编排 → 冻结发布批次。

### 5.1 兴趣估计

先使用可靠 UP、已确认分类、视频时长等特征；缺失特征不产生惩罚。首版不做标题 embedding，不引入模型依赖或逐条详情请求来补齐排序特征。

长期兴趣缓慢更新，会话兴趣快速更新且快速衰减；一次搜索、一次点击、一次快退不能主导画像。反馈按类型独立存储，每个视频贡献封顶，再做时间衰减：

```text
preference(k) = (sum(decayedEvidence(k)) + priorStrength * prior(k))
                / (effectiveEvidenceCount(k) + priorStrength)
confidence(k) = effectiveEvidenceCount(k) / (effectiveEvidenceCount(k) + priorStrength)
```

同一视频的点击、观看、点赞具有关联性，不能当成三个独立样本放大 confidence；证据数按不同视频计并封顶。长期与会话分别估计，长期画像不直接覆盖短期意图。所有权重与半衰期进入版本化策略，离线重放验证后填写，不作为官方参数发布。

### 5.2 基础得分

```text
base(v) = 1 / log2(sourceRank(v) + 2)  # rank 从 0 开始，仅在同来源批次内解释
score(v) = base(v)
           + bounded(confidence(v) * (longTerm(v) + session(v)))
           - exposureFatigue(v) - watchedPenalty(v)
```

各分量须归一化、缺失值安全且禁止 NaN；修正值范围和权重由策略版本统一提供。冷启动时兴趣修正为零。已观看不是一律屏蔽：区分完整观看、未看完长视频、距离上次观看时间；明确屏蔽在评分前执行。曝光后未点击仅产生有上限的疲劳，不等同“不喜欢”。

首版只在同批候选内重排，不跨来源比较 rank；兴趣修正最大位移暂定 3 位，同分按原 rank 稳定排序。新批次不得洗牌历史批次。后续跨批候选池必须单独评审来源分数校准及曝光偏差。

### 5.3 多样性与探索

逐条选择 score 减去与最近已选条目的相似惩罚，优先用 UP/已确认分类；考虑上一批尾部以免批次交界重复。软约束初值：相邻尽量不同 UP，最近 6 条同 UP 尽量不超过 2 条；候选不足依次放宽分类、UP 软约束，绝不放宽明确屏蔽。

REC-03 先只做局部稳定交换，所有调整共同遵守位移上限；上限内无法满足多样性时保留原序。REC-05 才实验探索，初值至多每 10 条 1 条，从官方候选中选择低本地证据但原序靠前内容；固定会话种子便于重放。不能用随机热门强行填充，不把“未知”认定为低质量。

## 6. 候选缓冲、刷新和分页

候选预取按距离视口约两屏触发，暂定最多保留 3 个未发布批次、候选总计 120 条；单会话已发布列表暂定上限 600 条。淘汰远离视口的旧批次时必须保留可见 BV 锚点及偏移，无法保证锚点时延后清理。封面预加载与有效曝光分离。

重复/过滤后空页不等于服务端结束：单次补位最多额外请求 2 批，串行、有取消边界；达到预算就停止自动补位，提供手动继续，不伪造 endReached。原始空是否代表终止由 REC-01 协议证据决定；网络失败保留列表，尊重限流并退避，不密集双源抓取。

刷新引入新批次，去重后前插，保留旧内容和现有回顶语义；给出新增数量或暂无新内容提示。模式切换后下一次刷新重建列表，失败保留旧内容，不混入迟到旧模式批次。返回播放页不触发强制洗牌。并发刷新的请求代数、账号代数和优化开关代数共同守卫提交。

## 9. 验证与发布门槛

纯 JVM 测试覆盖：原序冷启动、稳定排序、位移边界、缺失特征、衰减与时钟异常、反馈去重与撤销、样本相关性、软约束降级、曝光去重、长短视频满意度、存储淘汰/迁移、分页预算、关开/切号/清除与旧任务竞态。

集成验证：开关默认/升级/进程重启，关闭与基线的排序及请求序列一致（排除本来动态变化的服务端返回，使用固定样本），shadow 不改变输出；异常回退不丢列表、不绕过明确屏蔽。检查模块依赖与尺寸规则。

性能初始门槛：固定中端真机、120 候选，预热后 100 次端上排序 p95 ≤ 10ms，主线程无算法 IO；算法自有内存暂定 ≤ 8MiB（不含既有封面缓存）；单次自动补位不超过额外 2 请求，无无限重试。REC-01/02 记录设备/样本和基线，预算变更须有证据及评审。

质量评估同时记录有效观看转化、点击后快速返回、不感兴趣、重复曝光、新 UP 有效观看以及等待时间；按曝光定义提供分母，按视频长度/播放场景拆分。比较同账号的交替会话需说明兴趣变化与服务端动态候选的混杂因素，不能当作严格随机实验。离线重放仅验证策略性质，不能证明真实观看收益；若要评估新排序效果，需自愿设备内稳定分组实验并预先确定样本量和判定规则。实验组数据不直接混用更新另一组画像。

没有样本量前不宣称质量提升；首版收益目标是降低重复曝光，且有效观看/快速返回/负反馈不出现可信退化。不能只凭点击率或总停留时长判胜。无法得出结论则保留默认关闭和上一稳定策略。

实现 PR 运行相关模块 JVM 测试、:app:testDebugUnitTest、:app:assembleDebug 及仓库依赖检查；涉及存储序列化追加 release/R8 验证。人工覆盖：双列/大卡/平板、快速滚动、刷新/分页失败、返回位置、游客/多账号、开关连切、清除后重开、旋转/画中画/后台播放/退出恢复进度。文档 PR 不运行 Android 构建，不将此记作实现验收。
